# 0701: メタデータの原子的な書き込み（Atomic Store）

- 元ページ: https://trialofcode.org/database/0701_atomic_metadata/

## このステップで学ぶこと
- 複数のSSTableファイルを管理する際に必要になる「メタデータ」の役割を理解する
- 電源断などの障害が起きてもメタデータを安全に更新するための、原子的（atomic）な書き込み手法を実装する

## 要点
- LSM-Treeでは複数レベル・複数ファイルのSSTableが存在するため、固定のファイル名だけでは「今どのファイルが有効か」を管理できない
  - そのため、有効なファイル名の一覧などをメタデータとしてDB自身が記録する必要がある
- メタデータ更新中にクラッシュしても復旧できるように、ダブルバッファリング方式を採用する
  - 2つのスロットにそれぞれ `version` / `data` / `crc32` を持たせ、交互に書き込む
  - 例: `slot 0 -> [version 124 | data yyy | crc32]`, `slot 1 -> [version 123 | data zzz | crc32]`
- 復旧時は「デシリアライズに成功し、かつCRCが一致するコピーの中で、バージョン番号が大きい方」を正とみなす
- 主なコンポーネント
  - `KVMetaData`: バージョン番号とSSTableファイル名一覧を保持するデータ本体
  - `KVMetaStore`: 2スロット（`KVMetaItem`）を管理する層
- 主な操作
  - `Get()`: 2スロットのうち有効かつバージョンが大きい方を返す
  - `Set()`: バージョンが小さい方のスロットを上書きし、`fsync`を呼んでディスクへ確実に反映する
  - `Open()`: 破損している（デシリアライズ失敗やCRC不一致）コピーは無視して読み飛ばす

## 実装のポイント / 注意点
- 常に「書き込み中でない方（バージョンが古い方）」を上書き対象にすることで、更新中にクラッシュしても片方は必ず無事な状態を保てる
- 書き込み後の`fsync`を省略しない。これを怠るとOSのキャッシュに留まったままクラッシュ時に消える可能性がある
- 直列化フォーマットはJSONなど何でもよいが、CRC32によるチェックサム検証は必須
- このメタデータ機構は次のステップ（0702）でSSTableファイル名管理の基盤として利用される
