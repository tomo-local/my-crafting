# 0702: LSM木のメタデータ管理

- 元ページ: https://trialofcode.org/database/0702_lsm_metadata/

## このステップで学ぶこと
- 0701で作った原子的メタデータストアを使い、実際のKVストア全体のファイル管理に組み込む
- SSTableファイル名の動的な生成・追跡・復元の仕組みを実装する

## 要点
- 目的は「ユーザーはディレクトリパスを指定するだけで、DBがその中のファイル群を自動管理できる」ようにすること
- KVの構造
  ```go
  type KVOptions struct {
      Dirpath string
  }

  type KV struct {
      version uint64
      Options KVOptions
      meta    KVMetaStore
      log     Log
      main    SortedFile
  }
  ```
- ファイルは固定名のものと動的名のものに分かれる
  - 固定ファイル: ログ（`kv_log`）、メタデータの2スロット（`meta0`, `meta1`）
  - 動的ファイル: SSTable（`sstable_1`, `sstable_2`, ... のようにバージョン番号で命名）
- `version`は単調増加するカウンタで、新規ファイル名の採番と、再起動時の状態復元の両方に使われる
- コンパクション（不要ファイルの整理）の安全性向上
  - 従来の「`rename()`で置き換える」方式から、「先にメタデータへ新ファイルを記録してから旧ファイルを削除する」方式に変更し、原子性を高めている
- 起動時は `kv.version = kv.meta.Get().Version` のようにメタデータから状態を復元する

## 実装のポイント / 注意点
- ファイル名の採番と実際のファイル作成、メタデータへの反映の順序を誤ると、クラッシュ時に「メタデータにはあるがファイルが存在しない」または逆の不整合が起こり得るので、書き込み順序を意識する
- 「メタデータ更新→旧ファイル削除」の順序を守ることで、途中でクラッシュしても最悪旧ファイルが残るだけで済み、データ消失は防げる
- この仕組みが整うことで、次ステップ（0703）で複数レベルのSSTableを扱う土台ができる
