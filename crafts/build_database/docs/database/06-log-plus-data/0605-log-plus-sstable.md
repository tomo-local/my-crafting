# 0605: ログ + SSTable（Log + SSTable）

- 元ページ: https://trialofcode.org/database/0605_log_compact/

## このステップで学ぶこと

- MemTableとSSTableの2階層構造を実際に統合し、クエリ結果をマージして返す仕組みを完成させる
- コンパクション（Compact）処理により、2階層を1つのSSTableにまとめ直す方法を学ぶ

## 要点

- `KV` 構造体に `main SortedFile`（SSTable本体）を追加し、メモリ内データと永続化データを分離管理する
- クエリ時はMemTableとSSTable両方から結果を取得し、0604のマージソートで統合する
- 階層が2つ以上になると、上位レベルで削除マークを残さないと下位レベルの古いデータが復活してしまう問題が生じる
  - 対策として `SortedArray` に `deleted []bool` を追加し、削除状態を追跡する
  - 現時点ではMemTable（上位）にのみ必要で、SSTable（下位）には不要
  - 将来LSM-Treeで中間レベルが増えると、そこにも削除マークが必要になる
- マージ後は重複キー・削除キーが除去されるため、最終的なキー数は各レベルの合計より少なくなる
  - 事前にオフセット配列のサイズを見積もって確保し、マージ後に正確なキー数を書き込む方式を採用
  - その結果ファイル内にギャップが生じるが、これは許容している
- Compact処理でのファイル置き換えは、Linuxの `rename()` のアトミック性を利用する
  - 永続性を保証するため、親ディレクトリのfsyncも併せて実行する

## 実装のポイント / 注意点

- 新規メソッドの役割分担
  - `KV.Compact()`: MemTableとSSTableをマージし、新しいSSTableを生成する
  - `MergedSortedKV.Seek()`: 各レベルの `Seek()` を初期化し統合イテレータを作る
  - `filterDeleted()`: 削除キーを除外するラッパー
- Compactの流れは3ステップ
  1. MemTableとSSTableをマージして一時ファイルに出力
  2. 元のSSTableを一時ファイルでアトミックに置き換え（`rename()` + `fsync`）
  3. MemTableとログをクリアする
- 削除状態を記録し忘れると、クエリが削除済みのはずの古いデータを返してしまうので要注意
- この段階でLSM-Treeの基本形が完成し、以降のステップで複数SSTableレベルへ拡張されていく
