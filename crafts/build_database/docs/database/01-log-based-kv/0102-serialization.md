# 0102: バイナリシリアライゼーション

- 元ページ: https://trialofcode.org/database/0102_kv_encode/

## このステップで学ぶこと

- メモリ上のキー・バリューをディスクやネットワークに送れるバイト列に変換する（シリアライズ）
- バイト列から元のデータ構造に復元する（デシリアライズ）
- `io.Reader`/`io.Writer`を使い、ファイル・メモリ・ネットワークなど異なる入出力先に統一的に対応する

## 要点

- シリアライゼーションはメモリ上のデータをバイト列に変換する処理、デシリアライゼーションはその逆
- 採用するフォーマットはシンプルなバイナリ形式
  ```
  | キーサイズ(4B) | バリューサイズ(4B) | キーデータ | バリューデータ |
  ```
  サイズはリトルエンディアンの`uint32`（`binary.LittleEndian.PutUint32()`で変換）
- 可変長のキー/バリューの境界を特定するため、先頭にサイズ情報を置くことでパーサをシンプルに保てる
- バイナリ形式を選ぶ理由
  - 実装がシンプル（テキスト形式のようなエスケープ処理が不要）
  - CPU効率が高く、JSON等より高速
- テキスト形式（JSON/XML）は一見直感的だが、デリミタのエスケープや64ビット整数・バイナリデータの扱いで複雑化しやすい
- ProtobufやMsgPackのような既存ライブラリもあるが、単純な用途では自前のバイナリ形式を実装する（車輪の再発明）のも実務的な選択

## 実装のポイント / 注意点

- エンコードはサイズが事前にわかるため単純にバイト列を組み立てられる
  ```go
  func (ent *Entry) Encode() []byte {
      data := make([]byte, 4+4+len(ent.key)+len(ent.val))
      binary.LittleEndian.PutUint32(data[0:4], uint32(len(ent.key)))
      binary.LittleEndian.PutUint32(data[4:8], uint32(len(ent.val)))
      copy(data[8:], ent.key)
      copy(data[8+len(ent.key):], ent.val)
      return data
  }
  ```
- デコード側は呼び出し元が事前にサイズを知らないため、`io.Reader`から段階的に読み込む設計にする（まずサイズヘッダを読み、それを元にキー・バリュー本体を読む）
- `io.Reader`/`io.Writer`という抽象インターフェースを使うことで、ファイル・メモリバッファ・ソケットなど異なるリソースに同じロジックを適用できる
- 次ステップ（ログの読み書き）では、このEncode/Decodeがログファイルへの追記・読み出しの基礎になる
