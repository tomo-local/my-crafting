# 0104: fsync

- 元ページ: https://trialofcode.org/database/0104_fsync/

## このステップで学ぶこと

- データベースが「ディスク書き込みの永続性」をどう保証するかを理解する
- OSのページキャッシュとfsyncの関係を理解し、Goで`Sync()`を使って明示的にディスクへ反映させる
- ファイル作成・削除・リネーム時に親ディレクトリのfsyncも必要になるケースを知る

## 要点

- 耐久性（Durability）の定義: 「成功を返した時点で、そのデータは確実にディスク上に存在する」という保証。呼び出し元が成功を受け取った後にクラッシュしてもデータは失われない
- ファイルへの書き込みは直接ディスクに到達せず、OSのページキャッシュを経由する
  - 複数の書き込みをまとめてスループットを上げる仕組みだが、電源喪失時にデータが失われるリスクを生む
- fsyncシステムコールは全キャッシュ層をフラッシュし、完了を待つ。Goでは`*os.File`の`Sync()`メソッドで呼び出す
  ```go
  return log.fp.Sync() // fsync呼び出し
  ```
- ファイルの作成・削除・リネームでは、Linuxでは親ディレクトリに対してもfsyncしないとメタデータ変更が保存されないことがある
  ```go
  func syncDir(file string) error {
      dirfd, err := syscall.Open(path.Dir(file),
          os.O_RDONLY|syscall.O_DIRECTORY, 0o644)
      defer syscall.Close(dirfd)
      return syscall.Fsync(dirfd)
  }
  ```
- Go標準ライブラリはディレクトリのfsyncを直接サポートしないため、`syscall`を直接呼ぶ必要がある（Windowsではこの処理自体が不要）

## 実装のポイント / 注意点

- Linux固有の挙動（ディレクトリfsync）に依存する箇所はOSごとの分岐が必要になる可能性がある
- fsyncだけでは不十分: ログレコードの書き込み途中でクラッシュすると、レコードが「半分だけ書き込まれた」状態になり得る（torn write）
  - これはfsync単体では解決できず、次ステップ（0105: チェックサム）でアトミック性の問題として扱われる
- fsyncの呼び出し頻度はパフォーマンスとのトレードオフになる（毎回呼ぶと安全だが遅い）が、本チュートリアルではまず正しさを優先する設計になっている
