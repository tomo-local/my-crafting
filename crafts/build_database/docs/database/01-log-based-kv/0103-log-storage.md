# 0103: ログストレージ

- 元ページ: https://trialofcode.org/database/0103_log_rw/

## このステップで学ぶこと

- アペンドオンリー（追記専用）ログにエントリを書き込み、順序通りに読み戻す仕組みを実装する
- 起動時にログ全体を読み込んでメモリ上の状態を再構築する処理を実装する
- 更新（set）と削除（del）を区別できるログフォーマットを設計する

## 要点

- アペンドオンリーログは「ファイル末尾にのみ追記し、既存エントリは変更・削除しない」という原則で動作する
  - 各操作を記録し、順序通り適用することで最終状態を再現できる（インクリメンタル更新）
  - 状態変化を完全に記録するため、複製（レプリケーション）やロールバックに応用できる
  - ログは無限に肥大化できないため、あくまで補助的な役割（古いレコードの扱いはLSM-TreeやB+Treeと統合する後続ステップで解決）
- Entryのフォーマットに「削除フラグ」を追加し、set/delの2種類の操作を区別する
  ```
  | キーサイズ(4B) | 値サイズ(4B) | 削除フラグ(1B) | キーデータ | 値データ |
  ```
- `Log`構造体の責務
  - `Open()`: ファイルを読み書きモードで開く（存在しなければ作成）
  - `Write(ent *Entry)`: エントリを末尾に追記
  - `Read(ent *Entry)`: エントリを順に読み込み、末尾で`io.EOF`を返す
  - `Close()`: ファイルをクローズ
- `KV`構造体に`log Log`を追加し、`Open()`時にログを最初から最後まで読み込んで`mem`に適用する
  - 同じキーに複数の操作が記録されている場合、後のものが優先される

## 実装のポイント / 注意点

- `Set`/`Del`は既存のメモリ操作に加えて、ログへの書き込みも行うよう拡張する
  - `Set`: 削除フラグ=falseでエントリを記録
  - `Del`: 削除フラグ=trueでエントリを記録
- Encode/Decodeの実装では、ファイル末尾での`io.EOF`を正しく呼び出し元に伝播させる必要がある
- 現時点での未解決の課題（後続ステップで対応）
  - 書き込み中の電源喪失に対する保護がない（0104: fsyncで扱う）
  - OSのファイルバッファがディスクに確実に反映される保証がない（0104: fsync）
  - ログサイズが無制限に増え続ける問題（将来のマージ処理で対応）
- 「後から書かれたエントリが先のエントリを上書きする」という適用順序のルールを、リカバリ処理で厳密に守ることが重要
