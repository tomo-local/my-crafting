# 0101: KVインターフェース

- 元ページ: https://trialofcode.org/database/0101_kv_interface/

## このステップで学ぶこと

- インメモリのキー・バリュー（KV）ストアの基本インターフェースを設計・実装する
- KVストアがより複雑なデータベース（リレーショナルDBなど）の基盤になっていることを理解する
- OLTP（本チュートリアルの対象）とOLAPの違いを把握する

## 要点

- データベースは大きく「メモリ型」（Redis, Memcached）と「ディスク型」（MySQL, SQLite）に分かれるが、複雑な実装もシンプルなKVストアを土台に組み立てられる
- KVストアは辞書型の`get`/`set`/`del`操作を提供し、リレーショナルDBはその上位レイヤーとして構築される
- OLAP（分析向け、リソース大量消費）とOLTP（リアルタイム応答が必須、操作あたりのコストがO(log N)程度に抑えられる）は要件が異なり、本プロジェクトはOLTPを対象とする
- インターフェースは以下の形：
  - `KV`構造体が`mem map[string][]byte`を保持
  - 操作は`Open()`, `Close()`, `Get()`, `Set()`, `Del()`
- キー・バリューを`[]byte`にする設計判断
  - 任意のバイナリデータを扱えるようにするため
  - Goのマップは`[]byte`をキーにできないため、内部的には文字列に変換して保持する
- 将来ディスクI/Oを追加することを見越して、すべての操作にエラー戻り値を持たせる
- `Set`/`Del`は状態変化（実際に変更が起きたかどうか）を戻り値として報告できるようにする

## 実装のポイント / 注意点

- 現時点ではメモリ上のマップのみで完結し、永続化は行わない（次ステップ以降でログとして書き出す）
- ACID特性のうち「Atomicity（原子性）」は文字通り「分割不可能」を意味するが、実装上は並行性の問題と永続性の問題を分けて考える必要がある
- 一貫性・分離性・永続性についても、抽象的な定義だけでなく個々のDB実装の具体的挙動を見て理解を深める必要がある（この段階では深入りしない）
- ここで決めたインターフェース（`Open`/`Close`/`Get`/`Set`/`Del`のシグネチャ）は後続ステップ（シリアライズ、ログ、fsync、チェックサム）でも一貫して使われるため、拡張しやすい形にしておくことが重要
