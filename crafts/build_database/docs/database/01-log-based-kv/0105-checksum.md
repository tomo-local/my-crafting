# 0105: チェックサム

- 元ページ: https://trialofcode.org/database/0105_checksum/

## このステップで学ぶこと

- ログへのレコード追記における「アトミック性」を実現する方法を理解する
- 電源喪失時の不完全な書き込み（torn write）をチェックサムで検出する仕組みを実装する
- 破損したレコードとファイル末尾（EOF）を区別してログ読み込み処理を安全にする

## 要点

- 不完全な書き込みの問題: ファイルシステムはセクタ単位（通常512B〜4K）でしかアトミック性を保証しないため、大きなレコードの追記中にクラッシュすると次のような状態になり得る
  - ファイルサイズは増えているがデータが不完全
  - ファイルサイズは増えているがデータが未書き込み
  - ファイルサイズが部分的にしか増えていない
  - ただし、既にfsync済みのレコードは保護される
- チェックサムはこうした不完全な書き込みを「検出」するためのハッシュ値。異なるデータはほぼ確実に異なるチェックサムになる性質を利用する
  - データベースの文脈では、ビット反転などの一般的な破損検出は副次的な目的であり、主目的はtorn writeの検出
- レコードフォーマットにcrc32チェックサムを先頭に追加
  ```
  | crc32(4B) | key size(4B) | val size(4B) | deleted(1B) | key data | val data |
  ```
- `crc32.ChecksumIEEE()`を採用する理由
  - 暗号学的ハッシュ（SHA256, MD5）より高速・軽量
  - 単純な加算チェックサムと異なり、全ゼロデータでもチェックサムがゼロにならない
- エラー種別を明確に区別する
  - `ErrBadSum`: チェックサム不一致（書き込み未完了）
  - `io.EOF`: ファイル終端に到達（それまでのレコードはすべて有効）
  - `io.ErrUnexpectedEOF`: ファイルが途中で終わっている（サイズヘッダは読めたがデータが不足）
- `io.ReadFull()`を使うと、要求バイト数に満たない場合に自動で`io.ErrUnexpectedEOF`を返してくれるため、`Decode()`の要件に合致する

## 実装のポイント / 注意点

- `Encode()`はチェックサム付きでエンコードし、`Decode(r io.Reader) error`はチェックサム検証を行うよう修正する
- ログ読み込み側（`Read(ent *Entry) (eof bool, err error)`）は、`Decode()`から返るエラーを見て「最後の不完全レコードを無視する（eof=trueとして扱う）」処理を実装する必要がある
- 重要な制限: レコードサイズヘッダ自体が壊れている場合、それが「最後のレコードの不完全な書き込み」なのか「本当のデータ破損」なのかを区別できない
- log + checksum + fsyncの3つを組み合わせることで、電源喪失後もデータの永続性とアトミック性を確保できる（SQLiteが単純なファイル書き込みより堅牢とされる理由の一つ）
- 今後、新しいデータ構造（インデックスなど）を追加する際は、ACIDのA（Atomicity）とD（Durability）を都度見直す必要がある
