# 0305: パースしたSQL文の実行

- 元ページ: https://trialofcode.org/database/0305_exec_stmt/

## このステップで学ぶこと

- これまでにパースした `StmtXXX` 構造体を、実際のデータベース操作（Select/Insert/Update/Delete）に接続する
- SQL文の実行結果を統一的な形式で返す仕組みを作る

## 要点

- `ExecStmt()` が中心的な実行関数で、型スイッチによってステートメントの種類を判定し、対応する実行関数に振り分ける
- 実行結果は `SQLResult` という統一構造体で表現する
  - SELECT系: `Header`（カラム名一覧）と `Values`（行データ）を保持
  - 変更系（INSERT/UPDATE/DELETE）: `Updated`（影響を受けた行数）を保持
- スキーマ管理の仕組み
  - テーブルのスキーマ情報はKVストア上に `@schema_テーブル名` というキーで永続化する
  - 同時にメモリ上のキャッシュ（`DB.tables`）を持たせ、毎回KVから読み直さずに済むよう高速化する
- CREATE TABLEの実行フロー: `StmtCreatTable` → `Schema` 構造体に変換 → KVストアに永続化 → メモリキャッシュに追加
- SELECTの実行は責務ごとに3つのヘルパー関数へ分割している
  - `lookupColumns()`: カラム名をインデックス番号に変換
  - `makePKey()`: WHERE句の等値条件を主キー行に変換
  - `subsetRow()`: 取得した行から必要なカラムのみ抽出
- 更新系（INSERT/UPDATE/DELETE）の各実行関数は、KVストアの更新が行われた場合は `count=1`、行われなかった場合は `count=0` を返すという共通仕様

## 実装のポイント / 注意点

- これまでの各ステップ（トークナイズ→値のパース→SELECTパース→各種文のパース）で作ったデータ構造をここで初めて「実際の副作用を持つ処理」に接続する段階であり、パース層と実行層を明確に分離しておくことが設計上のポイント
- スキーマのキャッシュとKV永続化の二重管理は、キャッシュの初期化（起動時にKVから読み込む処理）や整合性維持を意識しておく必要がある
- SELECTの3ヘルパー関数分割は、0303/0304で確立した「複雑な処理を小さな関数に分割する」方針の踏襲
- 次のステップ（0401）では、ソート・検索機能の追加に進む予定であり、現状は主キー単位の単純操作のみへの対応であることを踏まえておく
