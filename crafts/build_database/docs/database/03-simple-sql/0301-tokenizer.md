# 0301: トークナイザー

- 元ページ: https://trialofcode.org/database/0301_tokenizer/

## このステップで学ぶこと

- SQL文字列をプログラムが扱える構造化データに変換する最初の段階として、トークナイザー（字句解析器）を実装する
- `string → tokens → struct` というパイプラインの入り口部分を作る
- 例: `select a from t where b=1` のようなSQL文を、キーワード・識別子・シンボル・リテラルの並びとして読み取れるようにする

## 要点

- トークンは4種類に分類される
  - キーワード: `select`、`from` など
  - 識別子: テーブル名・カラム名
  - シンボル: `=`、`;` など
  - リテラル: 数値・文字列
- パーサーは `buf`（入力文字列全体）と `pos`（現在の読み取り位置）の2つの状態を持つだけのシンプルな構造体
- 左から右へ一方向にトークンを消費していく設計が全体の基本方針
- 名前（識別子）の判定ルール（`tryName`）
  - 先頭は英字またはアンダースコアのみ許可
  - 2文字目以降は英字・数字・アンダースコアを許可
  - 前後の空白は読み飛ばす
- キーワードの判定ルール（`tryKeyword`）
  - 大文字小文字を区別しない
  - マッチした文字列が単語の一部でないこと（後続が識別子文字でないこと）を確認する必要がある（例: `selectx` を `select` と誤判定しない）
- `isSpace`、`isAlpha`、`isDigit`、`isSeparator` などの判定用ヘルパー関数を使うことで各トークン種別の判定ロジックを簡潔に書ける

## 実装のポイント / 注意点

- トークナイザーの役割はあくまで「文字列を意味のある単位に切り出す」ことで、SQL文法としての意味づけ（SELECT文かどうか等）は次段階（パーサー）の責務として分離する
- キーワード判定で単語境界チェックを怠ると、`selected` のような識別子を `select` キーワードと誤認するバグが起きやすい
- 次のステップ（0302）では、ここで切り出したリテラルトークンを実際の値（整数・文字列）としてパースする処理に進む
